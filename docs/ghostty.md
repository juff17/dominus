# Ghostty

My [Ghostty](https://ghostty.org) configuration, in [`ghostty/`](../ghostty/). Every new window opens as a layout:

```
┌────┬─────────────────────────────────────────┐
│work│ btop (CPU only)                          │
│hub●├──────────────┬──────────────────────────┤
│────│ viewer       │ [dir] 1:zsh 2:claude ✻   │ ← tmux tabs
│▲ 2 │ files·diff·dv│ claude / shell           │
│+new│ (Alt+V)      │                          │
└────┴──────────────┴──────────────────────────┘
```

- **Top:** btop, showing only its CPU box. If btop isn't installed, htop runs instead.
- **Bottom right:** a tmux session with its tab bar at the top. Ghostty's tab keys drive tmux tabs. A tab's name is cut to 20 characters so more fit. When they still don't all fit, tmux keeps the active tab in view and a bold yellow `◀` or `▶` marks the side with tabs cut off. On the right, `☰ 3/12` says you're on tab 3 of 12.
- **Left:** the viewer, hidden until you show it with `Alt+V`; a new window opens without it, so the tabs take the whole row. It opens in Files (the yazi file manager, which previews documents), in the active tab's folder. `Alt+V` again hides it, and it comes back as you left it. Each Claude start or resume in the window points Files at that Claude's folder: straight away if Files is running, even hidden, otherwise the next time you switch to it. Tab switches it to Diagrams, the diagram viewer (`dv`), which shows the diagrams Claude draws. A header row shows both modes; click one to switch.
- **Alt+D:** the diagrams of the tab you're looking at, in a framed window titled with the tab, about 85% of the window (Settings › Layout) and centered, with the window you were in drawn dimmed round it: in the workspace, the active tab; in the hub, the tab of the session open beside the list, or else of the selected card. A background agent has no tab, so the hub shows its job's diagrams instead, titled with the agent: the open one's, or else the selected card's. A tab parked on a background job shows the job's too, since that's where it draws now. `Alt+D`, `Esc` or a click on the dimmed part closes it and puts you back where you were. It looks and closes like every other popup, but it's a tmux window: tmux drops the image passthrough `dv` draws with from a popup.
- **Todo:** a mode of the left pane, after Diff. It shows every repo's open todos grouped by category (bug, feature, follow-up, docs, question, other), with the active tab's repo first in each group. An item can also have a type (research, decide, action, review or chore), shown in color beside its repo; `t` cycles it, or `ghostty-todo add --type`. The selected one opens under its row: who added it, from which tab and branch, and its note. `enter` goes back to the tab that added it, even in another Ghostty window. If that tab is gone, a second `enter` opens a new tab in the item's worktree running `claude --resume` on the session that added it. Items come from the `/todo` skill, which has Claude run `bin/ghostty-todo` (Claude adds them only when you ask), or from the pane. `a` takes a message in your own words and hands it to Claude (Haiku 5.5 at medium effort, unless Settings says otherwise), which writes the title, category, type (when the message makes it clear) and note, and files it under the repo it's about: the one it names, even loosely, or the one where Claude finds what it mentions by searching the git repos on the list and beside them read-only, whichever tab you typed it in. Errands, and anything no repo holds, go under none: the message shows under "filing" with a spinner until the item replaces it, or with the error if Claude couldn't file it. `shift+a` adds one by hand: a title, a category, then a note, with the step you're on shown on the right. `m` marks todos and `w` hands the marked ones, or the selected one, to agents: one Claude per todo, started the way New agent starts a task (`launch` in `agents/launch.ts`), with Opus, auto mode and medium effort unless Settings says otherwise. Before `enter` starts them, `t` picks a new tab (behind the one you're on) or the background, `b` its own worktree (from the main checkout, the default) or the branch the todo was added on (a todo added outside git runs in Settings › General › Default folder when that folder is on disk, else in the folder the viewer has open, the active tab's, and gets that folder's choices: the row says how many go there; when that folder isn't in git either, `b` isn't offered), and `m` the model. The prompt is the todo's title and note, and asks Claude to mark it done with `ghostty-todo done` when finished. In its own worktree, which Claude names for the todo and ends with its id, Claude commits there and asks before merging into main, then asks again before removing the worktree; it does neither unasked. Settings › Todo › Before merging into main can make it never merge, leaving that to you. A handed-off todo shows `✻`, and its card says which agent has it; while the hub lists that agent, `enter` opens it in the hub beside the list, as the tray's Go does (`go` in `tray/navigate.ts`): a tab agent through a session of its own, so the workspace stays on its tab, and a background agent with `claude attach`. Done items stay under "done today" and are dropped after a week (Settings: Keep done items). The list is one file, `~/.local/state/agent-hub/todos.json` (`$XDG_STATE_HOME`), so every window shows the same list. An item added outside a git repo shows `none` as its repo.
- **Diff:** a mode of the left pane, beside Files. It shows the uncommitted changes of the repository your active tmux tab is in, against the last commit (staged, unstaged and new files): a summary of what changed, a row per file with its added and removed lines, and one file open in place under its row with its diff. It checks git every second, so it empties once you commit.
- **Ping:** when Claude finishes or asks for permission in a tab you're not on, that tab turns red. Claude sends no desktop notification; the Agents widget below shows it.
- **Alt+H:** the keys, in a popup over the workspace or the hub. Each feature (Anywhere, Tabs, Viewer pane, Diff, Diagrams, Todo, Hub, New agent) is a section down the left, with its keys on the right; it opens on Hub in the hub, Diagrams over the Alt+D window and Anywhere elsewhere. `/` filters every section at once. Keys that are easy to forget are in the theme colour. The keys come from one table, `viewer/help/help.ts`, so change it along with the table below.
- **Rail:** a strip down the far left, topped by the Dominus gear, in the theme colour, which turns a few times as the window opens. **work** and **hub** switch the window between this workspace and the agent hub, the counts under them are the agents that need you (▲), are working (✻), are done (✓) and are idle (○), **+ new** starts an agent, **? help** shows the keys (Alt+H), and **⚙ set** opens Settings (Alt+S). The hub button gets an orange dot while anything needs you. A tab running Claude carries the same glyph in the tab bar.

## Agent hub

The hub is the window's second view (the rail's **hub**, `Ctrl+Shift+B` for its board or `Ctrl+Shift+A` for the session it has open; `Ctrl+Shift+W` goes back to the workspace). It shows every Claude session on the machine, from every Ghostty window and the background (`claude --bg`):

- **Lanes** for task agents: **Needs you** (a permission prompt, a question, or a monitor that raised something), **Working** (with the command running now and for how long), **Done** (finished, and you haven't looked yet) and **Idle**. A lane that fills up keeps going: Needs you scrolls with a "▾ more" cue and never shrinks a card, Working drops to cards that show only the command, Done keeps its newest two as cards (Settings: Done cards before folding) and folds the rest to a line each, and Idle is a line each; Settings' Show the Idle lane turns it off, giving its room to the other three. An empty lane says so (*Nothing needs you*, *Nothing working*, …). With no agent at all and no filter, the lanes and the monitors give way to the Dominus gear, *All quiet. No agent is running.* and a **+ New agent** button (the gear is a kitty picture in the theme colour, `tui/gear.ts`, sent again each time the hub comes into view, since tmux drops what a hidden pane sends). A tab that parked its conversation in a background job is one card with that job: its state comes from the job, and Enter and `o` go to the tab.
- **Stopped background agents** show in Idle, dimmed, marked `■` and "stopped". A stopped agent is one Claude Code still lists as active (`claude agents --json`) but that has no process: after a reboot, or when Claude Code's background service went away. agentd asks for that list every five seconds (`agents/stopped.ts`). Enter opens it with `claude attach`, which restarts it from its saved conversation. `r` restarts the selected one without opening it, and `R` restarts every stopped one, asking first; both run `claude respawn <id>`. `x` stops it for good with `claude stop`, as for any background agent, and it leaves the board. Settings › Hub & monitors › Restart stopped agents (off by default) has agentd restart each stopped agent on its own, once per login (the marks are in `$XDG_RUNTIME_DIR/agent-hub/restarted/`), so one that stops again stays for you to look at. A session started as a monitor (`/pr-babysit`, `/pipeline-watch`, `/log-watcher`, known by the first prompt in its transcript) stays out of Idle stopped as it does live, and nothing restarts it: it would come back without its watcher, since Claude Code doesn't run tools again on a restart. Start it again from Alt+M. Tab agents aren't covered: a tab's Claude closed with its window comes back with `claude --resume`.
- **Monitors** in a tray below, which keeps room for five even when fewer run (Settings: Rows kept for monitors) and grows to about a third of the screen when more do: each Monitor a session armed (pr-babysit's `watch_pr.py`, log-watcher's `watch_logs.py` (`logger` before it was renamed), or any other), with what it watches, its latest event and when it came. A monitor is *watching*, *needs action* (its last event was a failed, manual, stuck or conflicted job, an error, a crash (the log-watcher's container or pod exited non-zero, ran out of memory, restarted or is in a BackOff), or an auth, setup or blocked problem, and you haven't seen it; Settings: Count as needing you), *stale* (its command no longer runs) or *ended* (it expired, failed, or went with its session's last process when the session was resumed; it leaves after five minutes (Settings: Ended monitors leave after)). One you stop, with `x` or by asking its agent, leaves at once. A session that's watching something stays in the strip; it shows in a lane only when it needs you. `x` on a monitor stops just that one: the hub ends the monitor's own process group, so the session and its other monitors keep running. The session sees only that its watcher died and re-arms it, so the hub also leaves a request (`$XDG_RUNTIME_DIR/agent-hub/stop-requests/`) that the re-armed pr-babysit, pipeline-watch or log-watcher watcher takes: it prints `[unwatched]` and exits, and the session stops instead of re-arming. A request is taken once, so asking the session to watch again works; one no watcher takes within an hour is ignored. Answering `a` to its question stops it without asking from then on, by turning off Settings' **Ask before stopping a monitor**; turn it back on there to be asked again.
- **Open a session:** Enter opens a hub tab's or a background agent's live session beside a list of the rest, and your keys go to it. A hub tab opens through its own grouped tmux session; a background agent opens with `claude attach`. A workspace tab doesn't open in the hub: Enter, a click on it in the list, or Go from the tray, Monitors, Approvals or Todo takes you to it in the workspace, as `o` does. `Ctrl+Shift+B` closes it and goes back to the board; `Ctrl+Shift+W` leaves it open for `Ctrl+Shift+A` to bring back with focus in it, from anywhere in the window. With none open, `Ctrl+Shift+A` opens the last one again, else the selected agent. `Alt+←` moves focus to the list beside it and `Alt+→` back into it. Moving through the list with `j` / `k` or the arrows shows each agent in the session as you go, once the selection rests, while focus stays in the list; a workspace tab, which doesn't open in the hub, leaves the session as it was. In the list beside it, `x` or `Ctrl+X` closes the selected agent (or stops the selected monitor), asking first, as on the board. Switching tabs in it, from its tab bar or with the tab keys, switches only what that pane shows, and the list follows to the agent in the new tab. A background agent's session has no tabs, so `Ctrl+Shift+T` there opens a terminal in a popup over the window, in the agent's folder: `Esc` closes it (and the shell in it), and `Ctrl+Shift+T` again moves it, shell and all, to the workspace as a new tab and takes you there.
- **Hub tabs:** the hub's tabs and the workspace's are kept apart. The open session's tab bar has only the tabs opened from the hub: one you open there (`Ctrl+Shift+T`) is a hub tab, which shows in the hub and never in the workspace, and its card says *hub tab*; a Claude you start in it by hand is tracked like any other agent. A workspace tab running Claude never joins the hub's tab bar; its Claude still has its card on the board and its row in the list, and opening it takes you to the workspace. Closing a workspace agent from the hub closes its tab in the workspace.
- **New agent** (`n`, or **+ new**): a task with a first prompt, run as a background agent (`claude --bg`) that lands in Working and opens beside the list with `claude attach`, in its own worktree (the default; Claude makes it first with EnterWorktree and names it for the task, led by the ticket key when the task gives one) or on the current branch (before any Claude session makes a worktree, the hub plugin's `fetch-before-worktree.sh` hook runs `git fetch` so it starts from the remote's latest; Settings › New agent › Fetch before a worktree turns that off). New agent starts tasks only: monitors (pr-babysit, pipeline-watch, log-watcher) start from Alt+M's [Monitors](#monitors), and the form says so under the prompt. Folder, model, permission mode, effort and Chrome are fields of their own, starting at Opus, auto and medium, with Chrome off; Chrome on starts the agent with `claude --chrome`, for the Claude in Chrome browser tools (Settings › New agent sets the defaults); recent folders are one keypress away (up to eight; Settings: Recent folders shown). They're ranked by z.sh's frecency from `~/.z` (`$_Z_DATA`), merged with the folders agents ran in, the folder you last started one in staying first; without `~/.z`, or with Settings' Rank folders by at last used, newest first. With Only git repos (the default) a subfolder or worktree counts as its repo and folders outside git are left out. Folder starts on the selected agent's repo, else the newest recent, else Settings › General › Default folder (`~/projects` unless you set another); Settings › New agent › Default folder can make it always that folder. Above Folder, Runs in picks **Select folder** (the default) or **Default**, for an agent that isn't about one repo: it runs in Settings › General › Default folder, and the form drops Folder's input and Recent. Branch starts on Current branch there (Worktree is still a choice when that folder is a repo), and each choice keeps the branch you picked under it.
- A done agent counts as seen once you open it, mark it (`e`), or its tab is the one in front.

The hub needs no Claude Code hooks. It reads what Claude already writes: each running session's `~/.claude/sessions/<pid>.json` (its status, what it's waiting for, its tmux pane) and its transcript (the prompt, the tool running, the last reply, the context used, and every Monitor with the events it delivered).

The theme is Verdigris, oxidised copper on old iron (`tui/palette.ts`): patina green for focus and buttons, copper for what needs you, blue for what's working, green for what's done and rose for a monitor watching, on near-neutral greys. Ghostty draws the terminal itself in it too (`config.ghostty`), so the tabs, shells, btop and Claude Code sit on the hub's background.

## Monitors

`Alt+M` (Settings › Keybinds can move it) opens Monitors in a popup, over the workspace or the hub. Its top edge names the view (*Monitors · 5 running*, *Monitors · PR*, *Monitors · Pipelines · ⏸ 4 waiting for you*, *Monitors · New log watcher*); the row under it shows the four views as bordered tabs with their counts, `Running 5`, `PR 7`, `Pipelines 6` and `Logs +`, and `tab` / `shift+tab` switch between them. Monitors are started here, not from New agent. `/` opens a filter row under that row in Running and PR: what you type filters as you type, the matches lit yellow, with how many it keeps (`2 of 7`) and, under the list, how many it hides; `↵` keeps the filter and goes back to the list, `esc` clears it and hides the row. A footer lists the keys.

- **Running:** every monitor agentd knows, the same ones as the hub's monitors strip, grouped **▲ Needs you**, **◉ Watching** (◌ stale ones last) and **✓ Ended** (they leave after Settings › Hub & monitors' Ended monitors leave after), each with its state, kind (`PR` mauve, `PIPE` sapphire, `LOGS` green), what it watches (`gh gad #77`, `gl platform/api !512`, a pipeline as `platform/api v2.14.0` or `platform/api #4512`, or a log watcher's description), its latest event and how long ago. The view row's right side counts them by state. Beside the list, the selected monitor: its kind and target, the PR's title and branches when the PR list has it, where it runs (a background session or a tab), its skill, model and age, what it watches and until when if the drawer below started it, and its latest event. `j` / `k` move, `↵` opens its session in the hub (as the tray's Go does) and closes the popup, `a` opens its approvals (below), `x` stops it the way the hub's `x` does (its own process group; asking first until you answer `a`, Settings › Hub & monitors › Ask before stopping a monitor), `o` opens its PR in the browser.
- **What waits on you:** every babysit proposal (see [Approvals](#approvals)) comes from a monitor's session, and shows on that monitor's row: matched by the session that wrote it (its Claude session, else its tab's pane, as the tray matches it), and of that session's monitors the one watching the proposal's PR. A row with proposals says `▲ 2 to approve` in peach and moves to Needs you; the frame's title and the view row count them (`▲ 5 to approve`). Beside the list, the selected monitor's are in a peach box, **Waiting for you · 2**, one line each (the kind's glyph, the title, how long ago), above its latest event. A monitor that ended with proposals left stays under Ended (`▲ 1 left`) until they're settled, even once agentd stops listing it, while its session is there. A proposal whose session isn't known at all still gets a row of its own under Needs you, named from its PR, so nothing waits out of reach; `↵` there says the session is gone, and there's nothing to stop. Once the Claude session that proposed it has ended (it's no longer in `~/.claude/sessions/`) for a minute, agentd drops the proposal with `approval.py dismiss`, since nothing is left to hear how it went, and the row goes.
- **The approvals panel:** `a` on a monitor opens its proposals, the oldest first, in a panel beside the list (a footer note says so when nothing waits). The list narrows to state, kind and target, and the panel takes the rest (60% of the width; below 90 columns all of it): a peach edge, `Approvals · ci-playground !128 · 1 of 2` with a dot per proposal, then the proposal as the tray can't show it whole. A reply shows the comment it answers, the commit that addressed it, and the exact text it posts; a push its commits, its checks and the `git push` it runs. `←` / `→` step between the monitor's proposals; `a` approves, `shift+a` approves and sets Settings › Approvals to do that kind on its own from now on (never for a deployment), `e` edits a reply (in `$EDITOR`, or inline per Settings), `r` rejects (not yet, for a push or a move), `x` dismisses a failed one, `g` goes to the babysit session and closes Monitors, `o` opens the comment, job, run or PR in the browser. On a push `↑` / `↓` pick a commit, `space` keeps or drops it, `↵` shows its diff and `d` every change in the push: the diff takes the whole body, as the Diff mode shows uncommitted changes (a row per file with its counts and change bar, one file open under its row; `j` / `k` pick a file, `↵` opens or closes it, `J` / `K` scroll, `esc` goes back to the panel). `J` / `K` scroll a proposal too tall for the panel. `j` / `k` move to another monitor and the panel follows it (or says nothing waits on it); `esc` or `q` close the panel. Proposals that come or go are read every two seconds, as the list is. When the monitor's last one is settled here, the panel closes with a green note (`Retried · nothing left on ci-playground !128`) and the row goes back to its monitor's state.
- **PR:** your open GitHub PRs and GitLab MRs in one list, each tagged `gh` or `gl`: a mark (`[ ]` / `[x]`; the header shows `[-]` when some are marked), the repo and `#n` or `!n` (without your own namespace), the title, the pipeline (`✓ passed`, `✗ <job>`, `◐ running 3/9`, `⏸ manual <job>`, `— none`), the reviews (approvals of those required, changes requested, unresolved threads), the branch (`up to date`, `↓ 4 behind`, `⚠ conflicts`; GitHub doesn't say by how much) and its monitor (`◉ watching`, `▲ needs you`, or `+ attach`), matched to running pr-babysit monitors by the PR's address. Drafts are dimmed and come last; Settings › Monitors › Show drafts hides them. On the right of the view row, `Mine 7 │ Reviewer 2` (`w` switches: the ones you opened, or the ones you're asked to review or reviewed) and when the list was fetched (`⟳ 40s ago`). Under the list, the selected PR: its branches and age, its reviewers, and its clone with the branch the monitor will work on (`~/projects/platform-api · ⑂ babysit/512`), the clone found by its remotes among New agent's recent folders, the agents' folders and the git repos under `~/projects`, `~/src`, `~/code` and `~/work`. `j` / `k` move, `space` marks (and moves on), `*` marks all or none, `g` goes to the PR's monitor in Running, `o` opens it in the browser, `r` fetches again.
- **Where the list comes from:** `gh` for each host in Settings › Monitors › GitHub hosts (github.com) and `glab` for each in GitLab hosts (none until you add one), read-only and as JSON, with a time limit, off the drawing: one GraphQL call per GitHub host, and per GitLab host the user, two lists, then each MR's detail, approvals, discussions and, while its pipeline isn't green, its jobs. The last answer is kept in `~/.local/state/agent-hub/monitors/cache.json`, so the list opens at once with it while it's fetched again; it's fetched again only while the popup is open, every Settings › Monitors › Refresh every (60s), and on `r`. A host whose CLI isn't installed or isn't logged in shows one dim line in place of its rows; one that failed this time keeps its rows under a dim line saying so.
- **Attaching:** `↵` opens the attach drawer at the bottom, above the keys, for the marked PRs, or the selected one when none are marked. The list stays above it and keeps `j` / `k` and `space`; a long list scrolls to keep the selected row in view, and the drawer's first line says how many marked PRs are out of view (`Attach to 5 marked (3 off screen)`). It has three lines: who it's for and, on the right, `until merged · sonnet · medium effort · m more`; what to watch, `1` pipeline, `2` comments, `3` rebase, `4` ping on every comment (the first three on), which `1`–`4` turn on and off; and an optional one-line brief (`/` or `↵` to type it, `esc` back) beside **Start**. `m` opens until (merged, pipeline passes, 8h, 24h), model and effort as choices (`tab` moves between them, `←` / `→` change one), starting from Settings › Monitors' Watch by default, Until, Model and Effort. `ctrl+s` starts one background pr-babysit per PR (`launch` in `agents/launch.ts`), in the PR's clone, with the chosen model and effort, and its options after the PR's address in the prompt it starts with, then the brief, as typed, under `Brief:` in a paragraph of its own (pr-babysit's SKILL.md, Attach options); a PR with no clone found is left out and the footer says so. The options are kept by PR address in `~/.local/state/agent-hub/monitors/attached.json` (a month), which Running reads to show what a monitor watches. Then the drawer closes, the marks clear, and Running selects each new monitor once it shows. `esc` closes the drawer without starting anything.

- **Pipelines:** two groups. **Not from a PR** lists the pipelines (GitHub: workflow runs) of your projects (Settings › Monitors › Projects, as `host/group/project`; with none set, the projects your open PRs are in) on their default branch and on the refs Settings › Monitors › Branches and tags names (`default branch, v*`), the newest of each ref. **From watched PRs** lists the latest pipelines of the PRs a running pr-babysit monitor watches, while Settings › Monitors › Pipelines from PR monitors is on (the default; `P` turns it off and on). Each row: `gh` or `gl`, the project, the ref (or `!128` / `#77`), the trigger (`push`, `tag`, `schedule`, `MR`, `PR`, `manual`), the stages a glyph each (`✓` green, `✗` red, `◐` blue running, `⏸` peach manual, `○` waiting, `⊘` skipped; `+N` past what fits; on GitHub each job is a stage), what's happening now (`⏸ deploy:prod waits for you`, `◐ security · 2 of 3 jobs`, `✗ e2e failed`), its age, and its monitor (`◉ watching` when a pipeline-watch monitor watches it, `via !128` for a PR's, else `+ watch`).
- **Keeping it short:** a pipeline that passed, was canceled or was skipped goes once it started longer ago than Settings › Monitors › Keep finished (6h, 24h by default, 3 days, 7 days, or until a newer run); a failed one, or one with a prompt still waiting, stays. `x` hides the pipeline under the cursor until a newer run replaces it (kept by run id in the pipelines cache, and dropped from there once the host stops listing it); `u` brings back the last one `x` hid. The view row says how many are hidden (`3 hidden`). `/` keeps the pipelines whose project, ref, PR, trigger, state, failed job, or waiting job or environment has every word typed, the matches lit.
- **What waits for you:** every GitLab manual job and every GitHub deployment waiting on a protected environment you may approve is a prompt under its pipeline's row, in a dark panel, one line each (`Run deploy:prod-eu?`, the commit and stage or environment, `y run` `n skip`). `j` / `k` move through rows and prompts together; the prompt under the cursor is lit, boxed in peach, and the others stay dim one-liners. `y` runs the lit prompt with nothing more to confirm: the job is read again, and if it isn't waiting on the same commit any more the footer says so and nothing runs; otherwise GitLab's job is played (`glab api -X POST …/jobs/<id>/play`) or GitHub's deployment approved (`gh api -X POST …/runs/<id>/pending_deployments`), logged at info with the ids, and the pipelines are read again. `n` hides the prompt until its job changes (another commit or a new run), kept in the pipelines cache. `↵` hides or shows a row's prompts. The frame's title counts them (`· ⏸ 4 waiting for you`).
- **Watching a pipeline:** `m` starts a background pipeline-watch monitor on the row's pipeline, and `+` types one into the `+ watch` bar at the bottom (a pipeline or run address, or `project@ref`), `↵` to start it. Its prompt is `/pipeline-watch <address or project@ref>` then `Until: finished`, with Settings › Monitors › Pipelines' model and effort (Haiku, low) in auto mode, in the project's clone when one is found, else in Settings › General › Default folder; then Running selects it once it shows. `o` opens the pipeline, or the lit prompt's job, in the browser; `r` fetches again.
- **Where pipelines come from:** `glab` (per project its details, recent pipelines, tag pipelines and each kept pipeline's jobs; per watched MR its latest pipeline) and `gh` (per repo its details, recent runs and each run's jobs and, while it waits, its pending deployments; per watched PR its head commit's runs), read-only with a time limit, after the PR list and on the same timer: only while the popup is open, every Settings › Monitors › Refresh every, and on `r`. The last answer is kept beside the PR list in `~/.local/state/agent-hub/monitors/cache.json`, with the gates you skipped and the pipelines you dismissed. A host that can't be read is one dim line; a single project that can't be read is left out and logged.
- **Logs (New log watcher):** a form. **Environment** is a row of chips, Settings › Monitors › Environments (`local`, `qa`, `stage`, `eu`, `ca`, `us`); `local` is always first and can't be removed, and envs matching Settings › Monitors › Protected (none by default) show in red. **Source** under it is a row of radio buttons: `local` is Docker alone; any other env is Kubernetes or Elastic. Kubernetes is grayed out without `kubectl` on `PATH` or a kubeconfig file (Settings › Monitors › Kubeconfig, else every file in `$KUBECONFIG`, else `~/.kube/config`), and Elastic without an MCP server named for Elastic or Kibana in Claude Code's settings (user and local scope in `~/.claude.json`, project scope in the folder's `.mcp.json`); a dim line says why. With both grayed out, every env but `local` is too. Only files are read: nothing reaches a cluster or Elastic. `←` / `→` pick an env or source, skipping grayed ones; `↑` / `↓` move between fields. **Watch for** takes several lines (`↵` starts a new one) and is required; **Level** (warn and up, errors only, info and up), **For** (30m to 24h), **Model** and **Effort** start from Settings › Monitors › Logs (warn, 2h, Haiku, low). `ctrl+s` starts a background log-watcher in the active tab's folder (of the window Alt+M opened over), else in Settings › General › Default folder, shown beside Start (`/log-watcher watch · stage · Kubernetes · read-only · in ~/projects/x`), with the prompt `/log-watcher watch` and then `Environment:`, `Source:`, `Folder:`, `Level:` and `For:` lines, then a blank line and `Watch for:` over what you typed, as typed; the skill finds the kube context for the env itself, and polls Elastic every 5 minutes for an Elastic watch. A protected environment asks once more in the footer first (`ctrl+s` again starts it). Then Running selects it once it shows.

`bin/ghostty-monitors` opens it (`viewer/monitors/monitors-view.ts`), from `Alt+M`, from `Alt+A` (`bin/ghostty-approvals`: the panel on the monitor whose proposal has waited longest, or Running saying nothing waits) and from the tray's Edit and Review (`--approval <id>`: Running on that proposal's monitor, the panel open on it). It reads agentd's `state.json` and the proposals every two seconds and doesn't start agentd itself. `Alt+M` and `Alt+A` close it, but not while a reply is being edited in the panel; one pressed while a proposal is being settled closes it once that's done, and a second closes it at once.

## Agents widget

A Plasma panel widget puts the hub's agents beside the clock. It is the only alert: Claude sends no desktop pop-ups (claude/ has no notification hook, and Ghostty's `desktop-notifications` is off):

- **In the panel:** a glyph and count per kind: ▲ needs you, ✗ broke (a monitor saw a failed job, an error, a crash or a conflict), ✻ working, ◉ watching (◌ gone quiet) and ✓ done; ○ when nothing runs. Settings › Tray › Count picks which kinds it counts. A new ▲ or ✗ fills it with its colour for two seconds (Settings › Tray; 0 turns it off), and a ring stays around it until you open the inbox (Ring until the inbox opens). Settings › Tray can also pop up a KDE notification (`notify-send`) and play a freedesktop sound (`canberra-gtk-play`, else `paplay`), or a sound file of yours (Sound › custom file, then its path under Sound file), for a new ▲ or ✗, the sound only while Ghostty isn't the window in front unless you turn Quiet while Ghostty is focused off. When the tray command fails three times in a row, a red ! leads the counts, and the tooltip and the inbox say why and since when.
- **The inbox** (click it, or the shortcut you give it; its width and most height are in Settings › Tray): every item in those sections, needs-you first, each with its buttons. **Allow** and **Deny** answer a permission prompt, only while it's on screen, as in the hub; **Go** opens the agent's live session in the hub, beside the list of the rest, and brings Ghostty to the front (the workspace stays on its tab); **Open hub ↗** shows the hub. A row about something on GitHub or GitLab ends with a blue ↗ link that opens it in the browser: a proposal's comment thread, failed or manual job, the run a GitHub deployment waits in, or else its PR or MR; a monitor's job when its latest event names one, else the PR it watches. Keys: `j` / `k` move, `↵` presses the first button, `1` / `2` / `3` the first three, `o` the ↗ link, `x` dismisses an item until it changes (on a babysit proposal it rejects it), `esc` closes. Done items fold into one line until shown, unless Settings › Tray says not to, and leave once you open them.
- **Notes:** a session can post something only it knows needs you, a fix ready to push or a finished rebase, as a ▲ item: pr-babysit's `notify.sh` writes it to `$XDG_RUNTIME_DIR/agent-hub/notes/`. Go takes you to that session; Go or `x` clears it, and it's dropped after a day.
- **Babysit proposals:** anything a babysitter wants to do under your name (post a reply, push its commits, retry a flaky job, run a manual job, approve a deployment, move its commits after someone pushed) waits as a row with its own buttons: a reply shows the text it would post with **Post**, **Edit** and **Skip**; a push **Push**, **Review** and **Go**; a manual job **Run** and **Skip**; a flaky job, under ✗ broke, **Retry** and **Go**. Edit and Review open Monitors on the proposal's monitor, with the approvals panel on it. A job a proposal is about shows once, as the proposal, not again as the watcher's own ✗ line. A proposal that failed when it ran stays as a ✗ row to **Try again**, Go to, or dismiss. With Settings › Approvals › Also show buttons in the tray off, a row only opens the proposal in Monitors or goes to the session. See [Approvals](#approvals).
- It reads and acts through `ghostty-hub tray` (`tray/tray.ts`), the same agents the hub shows, so handling an item in one clears it in the other. It keeps agentd running while it's in the panel.

## Approvals

A PR babysitter (`/pr-babysit`) never sends anything under your name itself. It proposes, a script runs exactly what it proposed once you approve, and anything that goes wrong goes back to the babysitter:

1. **The agent proposes.** `approval.py propose` (in the skill's `scripts/`) writes one JSON file to `$XDG_RUNTIME_DIR/agent-hub/approvals/` with the whole action: the reply's text and the thread it answers; the commits, the lease and the branch for a push; the job for a retry or a manual job. The tray and Monitors (on the monitor of the session that proposed it) show it at once.
2. **You approve** in the tray or Monitors' approvals panel (`a` on the monitor, or `Alt+A`), after editing a reply if you like, or dropping commits from a push.
3. **`approval.py approve` runs it.** One `gh api` / `glab api` POST for a reply, a retry, a manual job or a deployment; for a push, a check that the worktree is still where it was proposed and that the remote branch is still at the lease (`git ls-remote`), then `git push --force-with-lease`. The tray runs it under `zsh`, so the tokens from `~/.zshenv` are there even though the panel didn't load your shell. What happened is written back into the file.
4. **The babysitter hears about it.** `watch_pr.py` checks the folder every two seconds between polls and prints an `[approval]` event for each settled proposal of its session: approved (with the reply as you edited it, if you did), rejected, failed and why, or handed back. Dropping commits from a push, and moving commits onto a head someone else pushed, are always handed back: the babysitter rebuilds the branch, reruns lint and tests, and proposes again. A failure stays in the tray as a ✗ row until it's tried again, proposed again or dismissed. A proposal, waiting or failed, whose session has ended goes a minute later (`agents/orphans.ts`).

Nothing is approved that you weren't shown. The tray offers Post only for a reply short enough for its preview, and Push only for a push that takes nothing off the branch; anything else opens in Monitors' approvals panel first. The panel keeps a reply's line breaks, lists the commits a force push would take off the remote, and scrolls (`J` / `K`) what doesn't fit, refusing `a` until all of it has been on screen; if the proposal you were reading is replaced or settled elsewhere, the next `a` only says so. `approve` checks again before it runs: a push that the worktree, the lease or the commits it removes no longer match is refused; a job whose commit is no longer the PR's head isn't run; a deployment approves only the environments it named, and only while all of them still wait. A proposal being approved can't be replaced or dismissed until it's done. Retries run on their own at most once per job name on a PR, since each retry gets a new job id, and never for a job whose real name or stage (looked up from GitHub or GitLab) says deploy, release or prod.

Settings › Approvals says which kinds run without asking: a retry (once per job), moving commits after a push, a GitLab manual job (never one whose name or stage says deploy, release or prod), a push, and replies (off, drafted for approval, or posted). A GitHub deployment or workflow approval always asks. Something run on its own still shows in the babysitter's briefing, marked auto. PR babysit's own section adds what the babysitter may do in the worktree: auto-fix review comments, auto rebase (off, when clean, always) and tray notes for finished stages; `watch_pr.py` prints them as a `[settings]` event whenever they change.

## Images

New agent's Task, Todo's prompts (`a`, `shift+a`'s title and note, and `e`'s title and note), and Monitors' two fields an agent reads (the PR attach drawer's brief and Logs' Watch for) take an image the way Claude Code does: `ctrl+v` reads the clipboard's image and puts `[Image #n]` at the caret. A terminal's own paste carries only text, so the image comes from `wl-paste` (Wayland) or `xclip` (X11), whichever is installed (`install/packages.txt` has both); a clipboard with no image, or neither tool, says so. Pasting a path to an image file, or a `file://` URI (a file manager's copy, or a file dragged onto the terminal), attaches a copy of that file instead. Each image is saved under `~/.local/state/agent-hub/images/` (`$XDG_STATE_HOME`), in `agent/` or `todo/` (`core/images.ts`). A placeholder is one character to the line editor (`tui/line.ts`): the arrows step over it, and one `backspace` or `delete` removes it, which takes its image out.

`claude`'s command line can't attach an image, so the agent's prompt ends with each placeholder's path (a monitor's, on a line after its others) and asks it to read them with its Read tool (`imagesLine`). A todo keeps its images in the store as `images: [{ n, path }]`: `a` passes them to `ghostty-todo file --image <path>…`, and the filer may read them and keeps their placeholders in the title or note; `w` hands them to the agent with the todo's title and note. A todo's card says how many images it has. New agent's images are removed after a month; a todo's once no todo names them for a day.

## Install

`./install.sh` sets it all up. Its walkthrough (`install/walkthrough/main.ts`, run with a Node that runs TypeScript, from PATH or fnm) asks four pages the first time: Optional parts (Settings › Layout › Header and Side panel, and the KDE widget, which only Plasma 6 can tick), Editor, Restart stopped agents and Default folder. It saves them to Settings and `~/.config/dominus/install.json`, then lists what's missing the way apt does: `ghostty`, `tmux` and `jq` always, `btop` with the Header, yazi (snap) and the diagram-pane plugin with the Side panel (noting Google Chrome, which diagrams render with, when it's missing), Claude Code, and the hub plugin (`install/walkthrough/plan.ts`). It installs nothing until you approve; `--yes` approves without a terminal, and `--reconfigure` asks again. Node.js 24 or later must already be installed.

Windows that are open during install keep their layout (`install/after-link.sh` records them); new windows get the new one. Links left from the dotfiles repo's old layout are replaced, and ones with no file here are removed.

The Claude Code hooks come with the hub's own plugin (`hub-plugin/hooks/hooks.json`, see [the plugin](#the-hub-plugin)):
- **SessionStart:** `bin/ghostty-claude-start` points the viewer at Claude's folder.

Diagrams come from the diagram-pane mod (`diagram-plugin/`, the `diagram-pane@dominus` plugin that `./install.sh` installs with the Side panel), which renders each one to a PNG and writes each session's tabs to a file for its tmux pane, or for its job when it runs in the background (`claude --bg`, outside tmux), under `~/.cache/claude-diagram-pane/panes/`. `dv` shows the file of the window's active tab (or, in the Alt+D window, of the tab it was opened for), and closes a diagram by rewriting it; the format is in the mod's README. ## How it works

Each window is one Ghostty split running two tmux servers, one inside the other:

- **The outer tmux** (`layout.conf`, socket `ghostty-layout`) lays the window out. It runs one session per window, with no status bar and no prefix key. Its panes are btop, the viewer and the tab session.
- **The tab session** (`tmux.conf`, socket `ghostty`) runs in the outer tmux's bottom-right pane and keeps your tabs. It has no prefix key either: `C-b` would swallow the key Claude uses to send a task to the background, and `C-b d` would detach the window's client and end the window.
- **The hub's tab session** (`hubtabs-<window>`, on the same server) is a detached session that `hub_tab_new` in `bin/lib/tabs.sh` makes the first time the hub opens a tab. It has the hub tabs and nothing else: no workspace tab is linked in. Earlier versions linked the workspace's Claude tabs in, so `agentd` unlinks any it finds there (`hubUnlinkArgs` in `agents/daemon.ts`), which leaves them in the workspace. With no tabs left it ends, and the next tab or session the hub opens makes it again. The session the hub opens is grouped with it rather than with the workspace's session, so a tab opened there lands here. It goes when the window closes.

Ghostty's own splits can't do this layout. Its D-Bus actions can open splits but not size them, and a `global:` keybind acts on every split of every window, so a script can't resize one split without moving the others. tmux sizes panes exactly, in one step.

The scripts in `bin/`:

- **`ghostty-surface`** is Ghostty's `command`, so it runs in every new split. In the first split of a new window, it builds that window's outer session at the window's size, then attaches to it. Any other split gets your shell. It also runs the outer panes: `ghostty-surface top` runs btop and `ghostty-surface tabs` runs the tab session. A new window has no viewer: `ghostty-viewer-toggle` adds it.
- **Keeping btop's height:** tmux shares a window resize out between the panes, so a `window-resized` hook puts btop back to its height (Settings › Layout, or `GHOSTTY_TOP_ROWS`) after one. That includes the resize on attach, when KDE maximizes a new window while its layout is being built.
- **`ghostty-viewer-toggle`** runs on `Alt+V`. Hiding moves the viewer's pane to a window of its own, `viewer`, which is never shown (`break-pane`), so yazi and dv keep running, with passthrough off so nothing they draw then reaches the screen; showing moves it back left of the tab session (`join-pane`, at Settings › Layout's width) and focuses it. With no viewer yet, or after `q` in dv closed it, it opens one (`open_viewer` in `bin/lib/layout.sh`), which holds focus while yazi asks the terminal its questions, since tmux hands the answers to the focused pane.
- **Keeping the viewer's share:** Ghostty opens a window small (around 83×28) and KDE grows it after, so a split made at the small size ends up far from its share once tmux shares the growth out. `open_viewer` adds a second `window-resized` hook that sets the viewer back, hidden or shown, to its percent of the row (Settings › Layout › Viewer pane width, 30 by default, or `GHOSTTY_VIEWER_SHARE`) after every resize.
- **`ghostty-claude-start`** sends the viewer's yazi to Claude's folder with `ya emit-to` (yazi runs with a client id per window), and leaves the folder in a file that Files reads when it next starts. It never opens the viewer or moves focus. It also saves where Node.js is, which Diff, Todo and Diagrams need and Ghostty's own PATH lacks. The viewer gets `DV_TABS` so Diagrams, Diff and Todo know which tab session to follow; `tmux.conf` touches `$XDG_RUNTIME_DIR/ghostty-layout/tab-changed` when the active tab changes, so they switch with it.
- **`ghostty-viewer`** runs the left pane's modes in turn: `yazi` (Files), `viewer/diff/diff-view.ts` (Diff), `viewer/todo/todo-view.ts` (Todo), `dv` (`viewer/diagrams/diagram-view.ts`, Diagrams) and any you added in Settings › Workspace, which run their command with `bash -c` in the folder Files was in. Which are on, their order and the one it opens in come from `viewer/modes.ts`, read again at each switch, so a change shows the next time the mode changes. It tells each mode the names of the modes that are on (`GV_MODES`, tab-separated), which one it is (`GV_AT`) and where `q` goes (`GV_QUIT`); a mode exits with 10 + a mode's number to switch to it. `yazi` can't choose an exit code, so it says where to go by whether it writes its `--cwd-file`: Tab and a click on a mode's tab do, `q` doesn't, and a click leaves the mode's number in the file `GV_NEXT_MARK` names first. An added mode goes to Files when its command exits, and waits for a key first when it fails, so a broken command can't spin. `yazi/init.lua` and `yazi/theme.toml` lay yazi out like the design: the mode header, a file list beside a wide preview, and a short status bar. `dv` draws images through tmux with kitty Unicode placeholders, so panning moves in whole cells.
- **`ghostty-todo`** is the todo list's command line: `add`, `file`, `list`, `done`, `undo`, `edit` and `rm` (`ghostty-todo help`). `file` adds the message as a filing item and runs `claude -p` with the filing model and effort from Settings (Haiku 5.5, medium) in the item's folder, sending `/todo` with the item's id, where it was typed and the message, so the todo skill (`hub-plugin/skills/todo`, its Filing section) does the filing, as `/pr-babysit` and `/log-watcher` do theirs. It runs in `dontAsk` mode with only the read-only search, `ghostty-todo add` and `ghostty-todo repos` allowed, and no other skill. Claude picks the repo, as the skill always does (`ghostty-todo repos` lists the candidates: the repos on the list and the git repos beside them), writes the item and runs `add --filing <id>`, which replaces the filing item with it, with no tab or session. If Claude exits without doing that, or runs past the time limit in Settings (3 minutes), `file` records the error on the filing item. Todo runs `file` in its own process group, so closing the popup doesn't stop it, and dropping the item kills the group. `add` records the repo (the main checkout, so a worktree's items count as its repo's), the branch and worktree, the tab's tmux pane, and the Claude session it runs under, found from its parent processes. It records only the pane, since a window shows in the hub's sessions too; Todo looks up the window's own session when it goes there. `viewer/todo/todo.ts` holds the store both share. Each write takes a lock folder beside the file and replaces the file whole.
- **Popups** all work one way (`docs/architecture.md`, Popups): a frame titled with the popup and the key that closes it, over the window you were in, dimmed. Each script opens a borderless popup over the whole window with `bin/lib/core.sh`'s `overlay`, and the view inside draws the frame (`tui/overlay.ts`), sized from Settings › Layout. Inside a popup tmux's own bindings don't apply, so each reads its own key (wherever Settings › Keybinds put it) and Ctrl+C as close, and a click outside the frame or on its close hint closes it.
- **`ghostty-todo-panel`** opens `alt+t`'s popup on the client it's given and runs itself inside it with `--panel`. It reads the window from the client's session, so the list follows that window's tab session, and runs `viewer/todo/todo-view.ts` with `TD_POPUP=1`: no mode header, and keys that close the popup instead of switching modes.
- **Settings** (`viewer/settings/settings-view.ts`, in a popup from `bin/ghostty-settings`) changes values the hub, the tray, Todo and pr-babysit's watcher used to have built in, in sections: General, New agent, Monitors, PR babysit, Approvals, Log watcher, Todo, Hub & monitors, Tray, Editor, Workspace, Layout, Viewers and Keybinds. General has Default folder: where an agent starts when nothing names a folder (New agent's last resort, a log watcher with no tab folder, a pipeline watch with no clone, a todo with no repo), `~/projects` unless you set another, and home when it isn't on disk; a value saved as Todo's old Default repo carries over to it. Monitors has four groups: PR (the hosts, Start on, Show drafts, Refresh every, and the attach drawer's Watch by default, Until, Model and Effort), Key (Open Monitors), Pipelines (Pipelines from PR monitors, Projects, Branches and tags, Keep finished, Model, Effort) and Logs (Environments, Kubeconfig, Protected, Level, For, Model, Effort). The PR and log monitors' model and effort keep their `newAgent.pr.*` and `newAgent.logs.*` keys, so saved values carry over, but show only there; their mode and Chrome stay in PR babysit and Log watcher. A row of words (Projects, Branches and tags, Environments, Protected) is typed in the footer, comma apart; Environments always keeps `local`, put first when you leave it out. A setting can show in two sections under a name for each (PR babysit's Auto push changes is Approvals' Push fixes to the PR); Approvals' Popup key is Keybinds' Approvals popup; a few rows only show a value set elsewhere (the Meta+A key). Workspace's viewer modes are one setting, `workspace.modes`, a list of `{ id, on }` with a `name` and `cmd` for one you added (its id starts `x-`); a built-in mode the list lacks comes back at its end, and at least one stays on. Its other rows: whether new windows open with the viewer shown, which mode it opens in, and whether Alt+T and Alt+D still open while Todo or Diagrams is off. Each change is saved as it's made to `~/.local/state/agent-hub/settings.json` (`$XDG_STATE_HOME`), which holds only what differs from the defaults, as flat `key: value` pairs. A changed setting shows a peach dot and its default under it. `settings/settings.ts` lists every setting with its default and range. A value that's missing, broken or out of range reads as its default. The "don't ask again" for stopping a monitor, which the hub used to keep in `prefs.json`, carries over.
- **Keybinds** (Settings › Keybinds, `settings/keybinds.ts`) moves the keys that work anywhere in the window. The alt keys (Help, Todo, Settings, Diagrams, Approvals, the viewer, New agent, the editor, Monitors) can take another alt and a letter or digit; Ghostty's (Workspace ↔ hub, Back to the board, New tab, Close tab, New window) another ctrl+shift and a letter or digit. A key another row has, or one the shell, Claude Code or Ghostty's own defaults use, is refused and not saved. `layout.conf` stays where each alt key's command is written: `bin/ghostty-keys` copies the `bind -n M-…` statement to the new key in `~/.local/state/agent-hub/keys.tmux.conf` and sources it into the layout's tmux, which also runs it as `layout.conf` loads. Ghostty's moved keys go in `~/.config/ghostty/keys.local.ghostty`, which `config.ghostty` includes, and Ghostty reloads its config on SIGUSR2. Alt+H shows the moved keys, and every popup shows and closes on its own (and no longer on its old alt key once moved). The Alt+D window shows its moved key and closes on it, and no longer on `alt+d`: the copied binding sends `dv` a key of its own (`core/keys.ts` `DIAGRAMS_CLOSE_KEY`) rather than `M-d`.
- **Your instructions** (`settings/prompts.ts`) for a task from New agent and a todo handed off with `w`: a Markdown file each in `prompts/` beside `hub/`, in this repo (`prompts/task.md`, `prompts/todo-handoff.md`). Git ignores them: the repo keeps `<name>.md.example`, and install (`after-link.sh`, through `copy_prompt_examples` in `bin/lib/core.sh`) copies each to its `.md` once, never over one you have, like a `.env.example`. Edit the `.md` to change them; Settings shows each one's path and how many lines it has, under Task in New agent and under Hand-off in Todo. A first prompt keeps the hub's words apart from yours: a paragraph starting `From the hub:` holds the worktree rule, what the hub adds (a todo's id, repo and how to mark it done) and these instructions, joined into one line; then `My prompt:` (or `My todo:`) and what you typed, line breaks kept. With nothing to add, the prompt is only what you typed. The hub's card skips that first paragraph, so it shows your words. HTML comments in a file are left out. Filing a todo has none: it runs the todo skill, which you change instead.
- **`ghostty-help`** opens Alt+H's popup on the client it's given, for `layout.conf`'s binding and the rail's button alike, and runs itself inside it with `--panel` to start `viewer/help/help-view.ts`. The window name it's passed (`work`, `hub`, `diagrams`) picks the section the list opens on. The rail finds its window's client with `list-clients`, since a click doesn't say which client made it.
- **`ghostty-diagrams`** opens the Alt+D window: a `diagrams` window in the outer session running `dv` with `DV_FRAME` (the frame and title) and either `DV_TABS` (a tab session to follow: the workspace's, or the `peek-<pane>` session of the hub's open session) or `DV_PANE` (one tab pane: the selected card's) or `DV_JOB` and `DV_TITLE` (a background agent's job, from `ghostty-diagrams <win> job:<id> <title>`), and `OV_UNDER`, the window it was opened from, which `dv` captures and draws dimmed round the frame as every popup does (`tui/overlay.ts`, `tui/backdrop.ts`). `layout.conf` runs it from the workspace, hands the hub a key of its own in the hub (`hub.ts` `DIAGRAMS_KEY`), and in the diagrams window sends `dv` its close key (`core/keys.ts` `DIAGRAMS_CLOSE_KEY`). `agentd` treats the diagrams window like the hub: the tab behind it isn't being looked at.
- **`ghostty-editor`** runs on `alt+e`. In the workspace it reads the active pane's folder from the window's tab session, which `layout.conf` names. In the hub, `layout.conf` hands the hub a key of its own (`hub.ts` `EDITOR_KEY`), and the hub runs it with `--dir` and the folder agentd has for the open session's agent, else the selected card's, so a background agent with no tab opens too; there it prints what went wrong for the hub's footer. Either way it opens `git rev-parse --show-toplevel` of it (or the folder itself, if Settings › Editor says so) with the editor's command from Settings › Editor, passing `-n` for a new window or `-r` to reuse one.
- **`ghostty-term`** is `ctrl+shift+t` in a background agent's session in the hub. The hub marks that pane with the agent's folder (`@peek_bg`, `hub/peek.ts`), and `layout.conf` runs this script there instead of opening a tab; it also knows the pane by its command (`ghostty-hub attach <job>`), so a session opened before the hub marked it works too. The terminal opens in the agent's folder as it is now, from agentd's `state.json` by the job id, since the agent may have moved (into a worktree, or out of one that's since gone); the folder the hub marked stands in while agentd doesn't have the job, and the home folder when neither exists. It opens a tmux popup on the client running `term-<pane number>`, a session of its own on the tab server in that folder, whose key table is `popterm` (`tmux.conf`): `Escape` detaches it, which ends the session (`destroy-unattached`) and closes the popup, and `User0` runs `ghostty-term --tab <session>`, which moves its window to the workspace's tab session (`ghostty-<n>`) and selects the work window; the session, left empty, ends and the popup closes with it. A Claude started in that terminal records `term-<n>` as its tmux session, so agentd also matches a `term-` session to the tab its window now is in (`paneOf` in `agents/daemon.ts`): once moved, its card has the workspace tab, and opening it from the hub takes you there. tmux drops a user key on its way into a popup, so while a terminal is open the layout server stops reading `\e[9001~` as `user-keys[0]`, and the script puts it back once no `term-` session is left. Meanwhile the tab server reads it, so in another window `ctrl+shift+t` still opens a tab beside the one you're on (except in panes outside the tab session, like the hub's list).
- **`ghostty-tabs`** closes a tab. `layout.conf` runs it with the tab session (the window's, or the hub's open `peek-<pane number>`). `--close <session> [<tab>] [keep]` closes a tab (`close_tab` in `bin/lib/tabs.sh`): the × on a tab, `ctrl+shift+x` and closing a tab agent from the hub all go through it. A workspace whose only tab it was gets a fresh tab in the same folder first, unless the close came from that workspace itself without `keep`, so closing a Claude tab from the hub never closes the window. Ghostty's own `alt+<digit>` tab keys are unbound in `config.ghostty`, as the tabs are tmux's, so the keys reach the program in the pane.
- **Tab keys:** Ghostty sends them as escape codes, and the outer tmux runs the matching command in the tab session, whichever pane has focus; in a session the hub opened, they act on that pane's own session (`peek-<pane number>`) instead, so a new tab there is a hub tab. `Ctrl+Shift+W`, `Ctrl+Shift+A` and `Ctrl+Shift+B` are sent the same way, and switch the outer session's window: the workspace, the hub's open session, the board.
- **The hub's windows:** `add_hub` in `bin/lib/layout.sh` gives each outer session a second window, `hub`, and a rail (`hub/rail/rail.ts`) down the left of both. Clicks on a rail pass through to it without selecting its pane, and it never keeps focus, like btop. It puts its own width back after a resize. `ghostty-hub setup` adds the rail and the hub to a window opened before they existed.
- **`agents/agentd.ts`** is the one process that watches the sessions, so every rail and hub together cost one. Once a second it reads the session files, the new lines of each transcript and the tab server's panes, writes `$XDG_RUNTIME_DIR/agent-hub/state.json`, sets each Claude tab's `@agent` glyph, which `tmux.conf` draws, and unlinks any workspace tab an earlier version left in a hub tab session. The hub and the rails start it when it isn't running and register in `clients/`; it exits a little after the last of them. `agents/model.ts` holds the logic that turns a session into a card, and `hub/hub.ts` and `hub/rail/rail.ts` draw.

New windows are told apart from splits you open yourself by their D-Bus window number, recorded in `$XDG_RUNTIME_DIR/ghostty-layout/<ghostty pid>/known`.

Settings you can change through the environment:
- `GHOSTTY_TOP_ROWS` (default: Settings › Layout › btop height, 10): rows for btop; set, it wins over Settings.
- `GHOSTTY_VIEWER_SHARE` (default: Settings › Layout › Viewer pane width, 30): the viewer's percent of the bottom row; set, it wins over Settings.
- `GHOSTTY_RAIL` (default 1): `0` leaves out the rail and the hub.
- `GHOSTTY_RAIL_COLS` (default: Settings › Layout › Rail width, 6): the rail's width; set, it wins over Settings.

Settings › Layout › Header (btop) and Side panel switch those two parts off for new windows: `ghostty-surface` leaves out the btop pane, and Alt+V (`ghostty-viewer-toggle`) says the side panel is off instead of opening it. The install walkthrough asks about both.

### The hub plugin

What the hub needs from Claude Code is one Claude Code plugin, `dominus` in `hub-plugin/`: the `pr-babysit`, `pipeline-watch`, `log-watcher` and `todo` skills, the Python they share (`hub-plugin/lib/py/agent_hub`), and the hooks above (`hub-plugin/hooks/hooks.json`). The Side panel's Diagrams come with a second plugin, `diagram-pane` in `diagram-plugin/`: the mod that draws them and the `make-diagram` skill (`/diagram-pane:make-diagram`). The repo root is their marketplace (`.claude-plugin/marketplace.json`), and a plugin from a local marketplace loads in place, so edits apply at the next session start (or `/reload-plugins`) without reinstalling. `./install.sh` installs them with `claude plugin marketplace add <repo>` and `claude plugin install dominus@dominus` (and `diagram-pane@dominus`, after `npm ci` in its folder); your own Claude settings, skills and plugins aren't touched.

As plugin skills, the hub starts them as `/dominus:pr-babysit` and so on (`ghostty/core/hub-skills.ts`); what reads a prompt back also knows the bare `/pr-babysit` of sessions started before the plugin.

### The Agents widget

`./install.sh --links` links the widget's folder, `plasmoid/dev.dotfiles.agents/`, to `~/.local/share/plasma/plasmoids/dev.dotfiles.agents` as one link (`install/after-link.sh`). It isn't under `ghostty/` because Plasma refuses a widget whose files are links that lead outside its folder. Check that Plasma sees it:

```bash
kpackagetool6 --type Plasma/Applet --show dev.dotfiles.agents
```

Then put it in the panel, once:

1. Right-click an empty part of the panel and choose **Add Widgets…**. A sidebar of widgets opens.
2. Type **Agents** in its search box.
3. Drag the **Agents** card onto the panel, left of the system tray, and let go. It shows as a small dark chip: `✻2` with two agents working, `○` with none.
4. Give it its shortcut: right-click the chip, **Configure Agents…**, **Keyboard Shortcuts**, set **Meta+A** (the inbox's header names it). Set it there rather than over D-Bus, which can crash KWin.

Plasma loads the widget's files when its panel starts, so after changing them, or if Agents isn't in the widget list yet, restart the panel: `systemctl --user restart plasma-plasmashell` (windows stay open).

If the chip shows **"Sorry! There was an error loading dev.dotfiles.agents … package does not exist"**, the folder isn't one link: `ls -la ~/.local/share/plasma/plasmoids/` should show `dev.dotfiles.agents -> …/plasmoid/dev.dotfiles.agents`. Run `./install.sh --links` to fix it, then restart the panel as above.

## Tests

Each UI keeps its decisions (keys, cursor and selection, prompts, layout, parsing) in a module that does nothing on import. The file that runs keeps only the drawing and the tmux and process calls. That way the decisions have tests beside them:

- **Agent hub:**
  - its model: transcripts, monitor events, lanes, fitting a full lane, and the commands a new agent runs.
  - `agentd`'s scanning (`daemon.ts`): sessions, transcripts read as they grow, tmux panes and which tab is being looked at, tab glyphs, which workspace tabs the hub links in, whether monitors still run, the single-copy lock, and clients.
  - the board's keys, selection and layout (`keys.ts`, `board.ts`), and prefs and recents (`prefs.ts`).
  - the New agent form, the rail, and the state client.
- **Agents widget:** its items (sections, what's new, dismissing), babysit proposals as rows with their buttons, and running `approval.py` for them.
- **Approvals popup:** its keys: stepping through proposals, a push's commits, drops and diffs, editing a reply inline or in `$EDITOR`, and approving with "always" (`approvals.ts`). `approval.py` itself is tested with the `claude` suite (`hub-plugin/tests/test_pr_babysit_approval.py`), against a fake `gh` and a real bare repo.
- **Viewers:**
  - `dv`'s zoom and pan math.
  - Todo: the store, and the view's keys, cursor, prompts, edit form and hand-off (`todo-ui.ts`).
  - Diff: git parsing, the file list and keys (`diff.ts`).
  - Diagrams: pane files, tabs and keys (`diagram.ts`).
  - Help: the filter and the overlay (`help/state.ts`).
  - The kitty graphics helpers, the PNG writer and the gear's sizing (`tui/kitty.ts`, `tui/png.ts`, `tui/gear.ts`).
- **Popups:** every popup's frame over the dimmed window, where clicks land and which keys close it (`tui/overlay.ts`, `tui/backdrop.ts`).
- **Monitors:** its keys, filter, marks and drawer (`viewer/monitors/state.ts`), its frames with a list longer than the screen (`draw.ts`), the rows and their matching (`rows.ts`), the attach options and the prompt line (`attach.ts`), finding clones (`checkout.ts`), reading `gh` and `glab` answers from fixture JSON (`forge.ts`, `pipelines.ts`), Pipelines' prompt navigation, y, n and ! (`pipe-state.ts`), finding kubectl, a kubeconfig and an Elastic MCP (`sources.ts`), the Logs form's envs, sources, keys, protected confirm and prompt (`logs-state.ts`), and starting and stopping with a fake world (`effects.ts`).

Drawing, and anything that needs a live tmux server, has no tests. The tests use only Node's built-in test runner:

```bash
./test.sh ghostty
```

That runs every `*.test.ts` under `viewer/` and `hub/`, so a new test file is picked up on its own. CI runs these and the `claude` module's tests on every push to main and every PR (`.github/workflows/tests.yml`).

### Trying a worktree's changes in the open Ghostty

The links in `~/.config/ghostty/` point at the main checkout. The scripts in `bin/` source `ghostty-lib.sh`, which sets `GHOSTTY_CONF` from its own real path, so whatever a script runs (`viewer/`, `hub/`) comes from the checkout that script lives in. Repointing a link under `viewer/` does nothing; repoint the `bin/` script the key runs. The tmux keys run `#{@conf}/bin/<script>`, and `@conf` is `~/.config/ghostty`.

1. Find the script behind the key in `layout.conf` (Alt+T runs `bin/ghostty-todo-panel`).
2. Check the change in a throwaway tmux server first, before and after, so you know you're about to test the fix and not a guess. For the Todo list:

   ```bash
   wt=<worktree>/ghostty
   tmux -L try -f /dev/null new-session -d -x 150 -y 30 "TD_POPUP=1 node $wt/viewer/todo/todo-view.ts $PWD"
   tmux -L try send-keys j        # whatever reproduces it
   tmux -L try capture-pane -p | head
   tmux -L try kill-server
   ```

   Run it again with the main checkout's path to see the bug still there.
3. Point the live link at the worktree's copy:

   ```bash
   ln -sfn <worktree>/ghostty/bin/ghostty-todo-panel ~/.config/ghostty/bin/ghostty-todo-panel
   ```

   A popup starts a new process each time it opens, so the next Alt+T runs the worktree's code. Something long-running needs a restart: the hub, say (see its `forever` loop in `bin/ghostty-hub`).
4. When you're done, merged or not, point it back before the worktree is removed, or the key breaks:

   ```bash
   ln -sfn ~/projects/personal/dominus/ghostty/bin/ghostty-todo-panel ~/.config/ghostty/bin/ghostty-todo-panel
   ```

## Limits

- **btop's pane** only displays. It ignores the mouse and never takes focus, so keys always go to the viewer or the tabs. If btop exits anyway, it starts again a second later.
- **Dividers:** the line under btop can't be dragged, so a drag that runs up over it doesn't resize btop. The divider beside the viewer still drags, until the window next resizes and the viewer goes back to its share. The hub's list beside an open session can't be dragged either, and puts its width back after a window resize.
- **Right-click** goes to the program under the pointer; tmux's own pane menu is turned off.
- **The first `Alt+V`** in a window starts yazi, which takes about a second to be ready. The viewer has focus throughout: yazi asks Ghostty about the terminal through tmux, and tmux gives the answers to whichever pane has focus; in Claude's pane one of them would read as Alt+P and open the model picker. Hiding and showing it after that is instant, as yazi keeps running.
- **Closing the last tab** closes the window. Only workspace tabs count: closing the last one also closes the window's hub tabs and whatever runs in them.
- **Ghostty tabs:** tabs made from Ghostty's own tab button don't get the layout.
- **Answering from the hub** (`a` / `d`) works for tab agents, and only while the prompt is on screen. A background agent's prompt is answered in its session (Enter). The same goes for Allow and Deny in the Agents widget.
- **Edit and Review in the Agents widget** open Monitors in the Ghostty window used last, which may not be the one in front.
- **Go in the Agents widget** brings the first Ghostty window to the front. With several layout windows open, the agent still opens in the right window's hub, but it may be another window that comes forward.
- **Sessions outside the layout** (Claude in another terminal or another tmux) show on the hub, but can't be opened from it.
- **An open session resizes its tab** to the hub's pane, the way two tmux clients on one window do; it goes back when you're in the workspace again.
- **`shift`+drag** selects across the whole window, btop and viewer included, since Ghostty sees one split.
